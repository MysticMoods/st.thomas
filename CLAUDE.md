# Claude working guide for the St. Thomas parish site

This repository is a instruction file.

## Project overview

This is a Next.js 15 app for the St. Thomas Church, Mangalassery website.

- Framework: Next.js 15
- UI: React 19, TypeScript, Tailwind CSS
- Motion: Framer Motion
- Content model: bilingual JSON content in `content/*.json`
- Admin dashboard: `/admin` with local authentication
- Public site: homepage plus parish sections and forms

The app is designed to be edited primarily through content files and the `/admin` dashboard rather than through hard-coded application logic.

## Working directory


When you need to build, run, or modify the site, operate in the project directory.

## Setup

From the `ST_THOMAS/` folder:

```bash
npm install
cp .env.example .env.local
```

Then edit `.env.local` before going live. Required values:

```bash
ADMIN_USERNAME=vicar
ADMIN_PASSWORD=mangalassery1893
ADMIN_SESSION_SECRET=change-me-to-a-long-random-string
```

Optional translation endpoint for auto-filled bilingual content:

```bash
TRANSLATE_ENDPOINT=
```

Online giving (Razorpay). Leave the keys blank and the donation section falls back to the bank
and UPI details in `content/donation.json`, with the checkout button switched off:

```bash
RAZORPAY_KEY_ID=
RAZORPAY_KEY_SECRET=
RAZORPAY_WEBHOOK_SECRET=
```

The webhook secret is optional but wanted in production: point a Razorpay webhook at
`https://<domain>/api/donate/webhook` for `payment.captured` and `payment.failed`, so a payment
is still recorded when the donor closes the tab before the page can confirm it.

Use a secure random value for `ADMIN_SESSION_SECRET`.

## Content model

The site is mostly data-driven.

- `content/*.json` stores card content, timings, notices, gallery items, clergy, etc.
- Many fields use bilingual shape like `{ "en": "...", "ml": "..." }`.
- The `/admin` dashboard allows editing JSON content on the site.
- `content/messages.json`, `content/subscribers.json` and `content/donations.json` are runtime-generated by the forms and the donation flow. They are git-ignored and should not be edited manually unless necessary.

Content keys are declared once in `CONTENT_KEYS` (`src/lib/types.ts`) and loaded in
`getContent()` (`src/lib/content.ts`). Adding a section means: a JSON file, a type, an entry in
both of those, and a row in `SECTIONS` in `src/app/admin/AdminApp.tsx` — the dashboard editor is
schema-driven and needs nothing else.

Sections added on top of the original demo:

| File | Section |
| --- | --- |
| `upcoming.json` | Dated events, plus the welcome popup that announces the next three |
| `obituaries.json` | The obituary column (homepage strip and the `/obituary` archive) |
| `committee.json` | The parish committee, directly under the parish priest |
| `donation.json` | Giving — funds, amounts, limits, bank and UPI details |

When changing content, preserve the existing schema and bilingual key structure.

## Admin dashboard

The dashboard authenticates with the credentials from `.env.local`.

- user ID: `ADMIN_USERNAME`
- password: `ADMIN_PASSWORD`
- session secret: `ADMIN_SESSION_SECRET`

The app rate-limits login attempts and validates the session server-side. Do not bypass or weaken that logic when modifying auth behavior.

## Deployment notes

This app writes content files and uploaded media to disk at runtime.

- Saves go to `content/*.json`
- Uploaded files go to `public/uploads/`
- Backups are stored under `content/.backups/`

This means the app is best hosted on a Node environment with a persistent filesystem. Vercel/Netlify-style serverless hosts are not suitable for the current dashboard save flow because the filesystem is read-only there.

## Build and debugging expectations

When working on this app:

1. Keep `ADMIN_SESSION_SECRET` unique and long in production.
2. Preserve bilingual content shape (`en` / `ml`) when editing JSON.
3. Run `npm run typecheck` after TypeScript changes.
4. Run `npm run build` before claiming the app builds successfully.
5. Prefer content-driven edits over hard-coded text when updating parish information.
6. Be careful with uploads and image paths; they are referenced from JSON and public assets.
7. Never weaken the donation flow: the signature check and the read-back of the amount from
   Razorpay in `src/app/api/donate/verify/route.ts` are what stop a forged payment being
   written into the parish record.
8. Avoid framer-motion `layoutId` inside a dialog. A shared layout animation there can keep the
   panel from unmounting, which leaves a dialog that cannot be closed.

## Common production caveats

- Do not commit `.env.local`.
- Change the demo credentials before public deployment.
- The demo content is fictional and should be replaced with real parish information before launch.
- The site uses `public/images/site` and generated upload paths; keep those directories intact.

## Practical build workflow

For a standard task:

```bash
cd ../ST_THOMAS
npm install
cp .env.example .env.local
npm run dev
```

Then validate with:

```bash

```

If you are making content-only changes, the app often reflects them immediately without a rebuild; if you are changing code, run a proper build afterward.
