# Claude working guide for the St. Thomas parish site

This repository is a instruction file.

## Project overview

This is a Next.js 15 app for the St. Thomas Church, Mangalassery website.

- Framework: Next.js 15
- UI: React 19, TypeScript, Tailwind CSS
- Motion: Framer Motion
- Content model: bilingual JSON content in `content/*.json`
- Admin dashboard: `/admin` with local authentication
- Public site: homepage plus parish sections and forms

The app is designed to be edited through its content files rather than through
hard-coded application logic. Staff edit those files on the pages themselves —
sign in, press **Edit this page**, and every section carries its own button.
The `/admin` dashboard is for what has nowhere else to live: the queues people
write into, and the work of running the site.

## Working directory


When you need to build, run, or modify the site, operate in the project directory.

## Setup

From the `ST_THOMAS/` folder:

```bash
npm install
cp .env.example .env.local
```

Then edit `.env.local` before going live. Required values:

```bash
ADMIN_USERNAME=vicar
ADMIN_PASSWORD=<set your own>
ADMIN_SESSION_SECRET=change-me-to-a-long-random-string
```

Optional translation endpoint for auto-filled bilingual content:

```bash
TRANSLATE_ENDPOINT=
```

Online giving (Razorpay). Leave the keys blank and the donation section falls back to the bank
and UPI details in `content/donation.json`, with the checkout button switched off:

```bash
RAZORPAY_KEY_ID=
RAZORPAY_KEY_SECRET=
RAZORPAY_WEBHOOK_SECRET=
```

The webhook secret is optional but wanted in production: point a Razorpay webhook at
`https://<domain>/api/donate/webhook` for `payment.captured` and `payment.failed`, so a payment
is still recorded when the donor closes the tab before the page can confirm it.

Use a secure random value for `ADMIN_SESSION_SECRET`.

## Content model

The site is mostly data-driven.

- `content/*.json` stores card content, timings, notices, gallery items, clergy, etc.
- Many fields use bilingual shape like `{ "en": "...", "ml": "..." }`.
- Each section is edited where it appears, through `EditableSection`
  (`src/components/admin/EditableSection.tsx`). There is deliberately no second
  editor in the dashboard: one file, one place to change it.
- `content/messages.json`, `content/subscribers.json` and `content/donations.json` are runtime-generated by the forms and the donation flow. They are git-ignored and should not be edited manually unless necessary.

Content keys are declared once in `CONTENT_KEYS` (`src/lib/types.ts`) and loaded in
`getContent()` (`src/lib/content.ts`). Adding a section means: a JSON file, a type, an entry in
both of those, and wrapping the section on its page in `<EditableSection section="key"
label="What it is called">`. The editor is schema-driven and needs nothing else — no
registration, no row in a list, and nothing to keep in step.

Sections added on top of the original demo:

| File | Section |
| --- | --- |
| `upcoming.json` | Dated events, plus the welcome popup that announces the next three |
| `obituaries.json` | The obituary column (homepage strip and the `/obituary` archive) |
| `committee.json` | The parish committee, directly under the parish priest |
| `donation.json` | Giving — funds, amounts, limits, bank and UPI details |
| `chapels.json` | The kurishupallis and filial chapels, and when Mass is said there |

When changing content, preserve the existing schema and bilingual key structure.

## Admin dashboard

The dashboard authenticates with the credentials from `.env.local`.

- user ID: `ADMIN_USERNAME`
- password: `ADMIN_PASSWORD`
- session secret: `ADMIN_SESSION_SECRET`

The app rate-limits login attempts (five per address per fifteen minutes) and
validates the session server-side. Do not bypass or weaken that logic when
modifying auth behavior.

In production neither the bootstrap password nor the cookie secret has a
default: an unset `ADMIN_PASSWORD` means no bootstrap login, and an unset
`ADMIN_SESSION_SECRET` means a random one made at boot. Development keeps the
demo values so a fresh clone runs. Do not reintroduce a shipped default for
either — a password printed in the repository is not a password.

## Operations

Running the site is a first-class part of the app, not an afterthought bolted on
outside it.

- **Accounts** live in `content/users.json` (git-ignored), one per person, with
  the password kept only as a scrypt hash. `ADMIN_USERNAME` / `ADMIN_PASSWORD`
  from `.env.local` are a bootstrap: they work only while no account exists, and
  stop the moment the first one is made. `src/lib/users.ts` owns all of it.
- **Roles** are `owner` and `editor`. An owner manages accounts and restores
  backups; an editor edits the site and may change their own password. The last
  owner cannot be demoted, suspended or removed — a parish locked out of its own
  dashboard has no way back in.
- **Sessions** are re-checked against the accounts file on every request
  (`currentSession()` in `src/lib/auth.ts`), so suspending somebody ends their
  session at once rather than in eight hours.
- **The activity log** (`content/audit.json`) records every content save,
  upload, hall decision, review decision, account change, backup restore and
  sign-in — including refused ones. Call `audit()` from any new route that
  changes something. It never throws.
- **Backups** are the twenty rolling copies already written before each save;
  `/api/admin/backups` lists, reads and restores them, and a restore is itself a
  save, so it can be undone.
- **Visits** are counted by the site itself in `content/analytics.json`: no
  third party, no cookie, no address stored, `/admin` never counted, and readers
  with Do Not Track set are skipped. `src/lib/metrics.ts`.
- **Faults** from the server and from visitors' browsers land in
  `content/errors.json` via `src/lib/report.ts`, folded by message so one bad
  afternoon does not bury everything before it.
- **`/api/health`** is public and says only whether the content can be read and
  the disk written. `/api/admin/health` is the fuller picture for the dashboard.

All the runtime files above are git-ignored. Never commit them.

## Letters

Every public form now writes back. `src/lib/mail.ts` posts, `src/lib/letters.ts`
holds the wording, and `content/outbox.json` records every attempt.

- **A letter never fails a visitor's request.** Use `post()` — fire and forget —
  on anything a visitor is waiting on; `send()` only where the result is needed.
  The booking is saved before the letter is tried, never after.
- **Nothing is lost when mail is unconfigured.** With no `MAIL_HOST` the letters
  are still written to the outbox marked `not-configured`, and the dashboard
  says plainly that none of it is being delivered.
- Letters are bilingual, English first, and never ask for a password or a
  payment — so nothing in them can be imitated to ask for one.
- Newsletter subscribers each carry a token; every newsletter carries the
  unsubscribe link that uses it, and `/unsubscribe` acts on arrival rather than
  asking anybody to confirm. `src/lib/subscribers.ts`.

## Units and classes

A ministry may be divided into groups: the family units, the Sunday school
classes. They are one shape, `groups` on a ministry in `ministries.json`,
because they are one question asked twice — which one am I in, and who do I
ring?

```json
{ "name": {"en": "Class 5", "ml": "..."}, "division": "A",
  "people": [{ "name": {...}, "role": {...}, "phone": "+91 ..." }] }
```

- `division` is kept apart from the name so "Class 5 A" and "Class 5 B" sort
  together. Leave it out where there is no division.
- `groupsLabel` names the tab — Units, Classes, Wards — per ministry.
- A person whose name is still blank is **not shown**. An empty row is the
  office's unfinished work, and the page says "Names to follow" instead of
  printing a line with nothing on it.
- Telephone numbers render as `tel:` links, so a number is dialled rather than
  copied out by hand.

## Answering people

Every message, hall request and office request can be answered from the
dashboard it is read in — `src/lib/reply.ts`, `ReplyBox.tsx`,
`/api/admin/reply`. The answer is kept beside the message it answers, with who
wrote it and what became of it, so a second person does not write back twice.

- **Email** goes through the same outbox as every other letter, and its outcome
  is recorded honestly — including `not-configured`, which means the words were
  kept but nothing was delivered.
- **WhatsApp** opens `wa.me` on the parish's own number with the answer already
  typed; the office presses send there. It is recorded as `handed-over`, never
  as sent, because the site cannot know. This needs no business account and
  costs nothing. Sending WhatsApp from the server would need the Meta Cloud API,
  a verified business and approved templates — a different undertaking.
- Messages carry an `id` from now on. Older ones are found by the moment they
  arrived, so nothing already written has to be rewritten to be answerable.

## The parish office

`/office` carries the three things people walk in to ask for: a Holy Mass
offered for somebody, a certificate copied out of the registers, and a prayer.
One route (`src/app/api/office/route.ts`) serves all three, because they share
everything that matters — throttle, honeypot, acknowledgement, dashboard queue —
and differ only in what is asked.

- Only one Mass intention is taken per day; the form greys out the days already
  spoken for, and the API refuses a clash rather than leaving it to be found at
  the counter. `GET /api/office` returns only the dates, never who asked.
- A prayer asks for no telephone number. A certificate and a Mass do, because
  the office has to reply to those.
- Marking a certificate **done** writes to the person who asked — that is the
  whole reason for taking the request online.

## Public forms


All four — contact, newsletter, hall booking, hall review — share
`src/lib/limit.ts`: one throttle per gate per address, plus a honeypot field
(`website`) that a person never sees. A filled honeypot is answered with a
cheerful success so whoever sent it learns nothing. Any new public form should
use both.

`appendRecord()` serialises writes per file. Two letters posted in the same
moment, or two families booking in the same second, would otherwise read the
same list and the second write would silently drop the first record.

## Finding things, and being found

- **Search** (`/api/search`) walks the content files on every query — no index
  to rebuild, so anything the dashboard saves is findable at once. It matches
  against both languages and returns both, and the page shows the side the
  reader is reading. Opened from the header, or with Ctrl/Cmd+K or `/`.
- **`/calendar.ics`** is a live subscribable feed of the mass timetable and the
  parish week, built from `mass.json` and `events.json`. Times are written as
  floating local values, because half past six means half past six. A change in
  the dashboard reaches every phone that subscribed.
- **`/obituary/[slug]`** gives each person a page of their own, so a family can
  send a link to their own mother rather than to a column of forty strangers.
  The slug is `name-id`; only the id is used to find them, so correcting a
  spelling never breaks a link already sent. Memorial pages are `noindex`.

## Money

Two flows, both with the same two rules, and neither may be relaxed: **the
signature is verified before anything is believed, and the amount is read back
from Razorpay rather than taken from the browser.**

- `/api/donate/*` — giving.
- `/api/hall/advance` — the hall advance, which turns a held request into a
  confirmed booking. Which booking a payment is for comes from the order's own
  notes, never from the browser, so nobody can pay for one day and confirm
  another.

## Deployment notes

This app writes content files and uploaded media to disk at runtime.

- Saves go to `content/*.json`
- Uploaded files go to `public/uploads/`
- Backups are stored under `content/.backups/`

This means the app is best hosted on a Node environment with a persistent filesystem. Vercel/Netlify-style serverless hosts are not suitable for the current dashboard save flow because the filesystem is read-only there.

`DEPLOY.md` is the operations manual: host choice and why, an Ubuntu walkthrough
with systemd and nginx, the nightly off-box backup, what to watch, how to deploy
a change, and the pre-launch checklist. Keep it current when any of this moves.

## Build and debugging expectations

When working on this app:

1. Keep `ADMIN_SESSION_SECRET` unique and long in production.
2. Preserve bilingual content shape (`en` / `ml`) when editing JSON.
3. Run `npm run typecheck` after TypeScript changes.
4. Run `npm run build` before claiming the app builds successfully.
5. Prefer content-driven edits over hard-coded text when updating parish information.
6. Be careful with uploads and image paths; they are referenced from JSON and public assets.
7. Never weaken the donation flow: the signature check and the read-back of the amount from
   Razorpay in `src/app/api/donate/verify/route.ts` are what stop a forged payment being
   written into the parish record.
8. Avoid framer-motion `layoutId` inside a dialog. A shared layout animation there can keep the
   panel from unmounting, which leaves a dialog that cannot be closed.

## Common production caveats

- Do not commit `.env.local`.
- Change the demo credentials before public deployment.
- The demo content is fictional and should be replaced with real parish information before launch.
- The site uses `public/images/site` and generated upload paths; keep those directories intact.
